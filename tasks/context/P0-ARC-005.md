# P0-ARC-005 — Technology-stack ADR

- Owner: `/root/product_risk_review`.
- Objective: select exactly one Alpha production control-plane/UI stack from the accepted Electron, Tauri and .NET bounded evidence; explicitly define any native-helper boundary.
- Product boundary: the selected stack installs, detects, verifies, configures, compiles and hands off. It must not generate media, expose a tool-side Generate/Run action or submit `/prompt`; H3 in ComfyUI remains the only media generator after user Run.
- Dependencies: accepted P0-ARC-002, P0-ARC-003 and P0-ARC-004 evidence; accepted ADR-001/002/004 and no-self-update ADR.
- Allowed writes: `docs/adr/ADR-003-technology-stack.md` only.
- Forbidden writes: prototypes, registry, schemas, root plan/lockfiles and production code.
- Locks: none.
- Required decision method: classify each candidate dimension as runtime-proven, static-only, blocked or external; never score blocked/static evidence as a runtime pass. Compare implementation velocity, package/C-drive cost, dependency/SBOM surface, renderer/service isolation, native Windows APIs, child/Job containment, filesystem/path safety, installer/signing, accessibility, offline build, update/security SLA and testability.
- Required Alpha decision: choose a single stack now or explicitly reject all if no safe conditional path exists. Current-host toolchain availability may decide Alpha feasibility but must not be presented as an intrinsic product-quality fact.
- Native boundary: list operations that must be implemented in a narrow signed native helper (for example pre-first-instruction suspended process/Job containment, handle/volume/reparse identity) versus operations allowed in the UI/control plane. Define typed versioned IPC, argument arrays, ownership, crash/upgrade/signing/SBOM rules and fail-closed behavior. Do not let a generic shell/command bridge exist.
- Build/update boundary: Alpha has no self-updater; dependencies and package targets are immutable; online spike packaging is not offline/reproducible release proof. State exact production gates before release claims.
- Accessibility/UX: assisted novice installer and form-based project setup remain requirements; this ADR does not implement UI.
- Acceptance: one candidate and one fallback/revisit trigger are unambiguous; downstream implementation tasks no longer need three stack paths; blocked evidence is preserved; open signing/VM/native/build gates remain explicit. ADR status remains Proposed until Root acceptance.
- Failure fallback: if no candidate can safely proceed, select none and block downstream stack-dependent tasks; do not blend three UI stacks or weaken process/path invariants.
- Unlocks after Root acceptance: P1-DET-001/002/003 and QA-001, plus production control-plane scaffolding tasks.
