# Component manifest 1.0.0

This immutable authority belongs to exactly one packaged application build and is read only from that application's embedded resources. Its exact `(app_id, app_version, app_build_id, catalog_resource, integrity.content_sha256)` tuple must also be bound by a signed build inventory outside this self-describing document; the manifest cannot attest to itself. Exactly one embedded catalog is accepted. It contains expected component bytes and policy inputs; it is not a remote catalog, download command, ownership ledger, delete permit, launcher manifest, or updater.

An immutable HTTPS locator is actionable only inside a later explicit install/repair transaction after app-catalog binding, license approval, role/destination validation, space reservation, download verification and ownership transaction gates all pass. Runtime dependency installation is forbidden. The schema never contains an absolute user path.

`creator` identifies who created the original work. `publisher` identifies who made the exact release available. `packager` identifies who produced the exact bytes named by `artifact_sha256`. The two explicit relationship fields distinguish same-party from different-party roles even when one legal entity fills multiple roles. A contiguous provenance chain binds the parties, immutable source revisions and every input/output byte identity. Every chain locator is independently checked for immutable HTTPS revision binding or a safe embedded app resource; the first and final locators are not the only trusted steps. `transformation` fixes the exact three-step event sequence for byte-changing builds and permits the named middle step alone to change bytes; original-byte republication preserves identity throughout. The packager is bound to an exact SemVer 2.0.0 producer version, content-addressed build ID, revision-anchored producer source locator/revision and build-recipe hash. Evidence is length/hash bound and its status is a strict union: declared-unverified contains pending evidence, verified-release-attestation contains verified source/package attestation, and verified-reproducible-build contains a verified reproducibility report. Unverified evidence is valid catalog data only while release remains blocked.

Producer HTTPS locators use the closed form `https://<host>/(revisions|commits)/<40-hex-revision>/source`; embedded producer sources use `app-resource:producer-builds/<40-hex-revision>/source`. Channel names and arbitrary locator shapes are not accepted. `producer_build_id` is SHA-256 of the RFC 8785 JCS object containing exactly `{build_recipe_sha256, producer_id, producer_source_locator, producer_source_revision, producer_version}`. It is therefore a content identity for that build record projection, not a free-form release label or an assertion about the final component bytes.

Fixed archives bind the outer artifact, entry manifest, canonical expanded-tree identity, entry count, total expanded bytes and maximum single-entry bytes. Those declarations are preconditions only: a later materializer must still enumerate and validate every actual archive entry, reject links/reparse points and verify the expanded result before commit. Native helpers and private media tools require signature metadata bound to the exact artifact hash and verification against the release trust store before materialization. Authenticode is an embedded-signature branch for a single PE artifact; Minisign/OpenPGP use a separately hashed embedded signature resource. A declaration is not proof of successful verification.

For `canonical_regular_files_v1`, every accepted archive member is a regular file with a canonical `/`-separated relative path. Directory entries are omitted; links, reparse intent, duplicate paths and collisions under Windows ordinal case-insensitive comparison are rejected. For each file create the exact object `{artifact_sha256,byte_length,path,type}`, where `type` is `regular_file` and the hash is over raw file bytes. Sort records by unsigned UTF-8 bytes of `path`; `entry_manifest_sha256` is SHA-256 of the RFC 8785 JCS array. `expanded_tree_sha256` is SHA-256 of: ASCII `minimax-h3-tool-expanded-tree-v1` plus NUL, followed for every sorted record by unsigned big-endian `uint32(path_utf8_length)`, the path UTF-8 bytes, unsigned big-endian `uint64(byte_length)`, and the 32 raw hash bytes. Integer bounds are checked before framing. The materializer recomputes both identities from extracted files and must not trust archive directory metadata.

The manifest itself always declares `manifest_grants_ownership: false` and `manifest_grants_delete: false`. A managed artifact becomes tool-owned only after all five exact proofs are available: verified byte identity, owned transaction commit, ownership-ledger entry, handle containment without reparse, and no active lease. A matched external artifact remains read-only and has `delete_authority: never`, regardless of hash equality; no manifest field may reclassify it. Managed destinations carry only a managed-root-relative logical path. The immutable packaged manifest contains no runtime candidate ID, observation reference or selected path for external reuse. It declares only that a later model-selection contract must bind an exact candidate to an exact observation document and revalidate handle identity before every read.

License text, notice, redistribution/source/attribution obligations and human review are independent authority. `pending_external` is valid catalog data but leaves the component blocked. An approved decision is scoped to named regions, delivery modes, and reviewed artifact/provenance sets. An Agent, hash or signature cannot approve a license.

Approved-set identities are calculated over every component that references the license record, sorted by unsigned UTF-8 bytes of `component_id + NUL + component_version + NUL + artifact_sha256`. `reviewed_artifact_set_sha256` hashes the JCS array of exact `{artifact_sha256,byte_length,component_id,component_version,source_kind}` records. `reviewed_provenance_set_sha256` hashes the JCS array of exact `{component_id,component_version,provenance_content_sha256}` records, where the provenance hash covers parties, transformation, every chain step, producer build identity and evidence/status. Any drift invalidates approval scope and requires a new human decision; recomputing a hash is not approval.

A revoked or superseded manifest cannot contain an eligible component. A non-active component is always blocked. An eligible component's dependency closure must resolve to exact active and eligible targets; after that, its license must be approved and its provenance evidence verified. These are catalog actionability gates only and still do not authorize an install transaction.

Every core object is closed. Validation order is envelope/version, root JCS integrity, exact schema, domain invariants, then cross-component closure. Unknown operational fields, mutable source refs, remote catalogs, role/destination mismatches, unsafe relative paths, archive link/reparse intent, dependency cycles and authority conflicts fail closed. Display-only extensions are integrity-covered but never interpreted.
